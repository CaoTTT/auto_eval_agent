# 人工评分基准对比功能：代码实现方案 v1.0

状态：设计稿，未修改或实施业务代码。日期：2026-09-15。

代码基线：`CaoTTT/auto_eval_agent`，`feat/bailian-request-throughput`，远端提交 `6c05c200cf6ec7ce7575b5c8e9676f6d9f40ffbf`。已同步核对新增校准 Prompt 之后的请求调度、Token 估算、阶段耗时及“最终回复内部过程信息泄露”修订。本功能以独立后处理方式接入。

## 1. 产品目标与首版范围

在已有任务结果页新增一个主入口 **“与人工评分对比”**。用户选择已导入的人工基准或上传人工评分 Excel，平台解析、对齐并计算统计指标。原来的测评数据导入、选择 Prompt、启动任务、队列、失败补跑继续按现有方式工作。

人工 Excel 一次导入、多次复用。已有历史任务可以直接对比，无须重新调用模型。同一份基准可以与不同裁判模型或不同 Prompt 的多个任务比较。

### 首版交付

- 仅接入 `compare` 模式，兼容 2/3 产品、文字/VQA 输入、录屏/长截图回答证据。
- 支持现有人工合并宽表、平台生成的简洁宽表，以及通过列映射适配的其他人工宽表。
- 支持稀疏标注：只标部分 Case、部分产品或部分维度也能导入。
- 支持人工基准版本、匹配预览、单任务及多任务人机统计、分歧筛选、Excel 导出。
- 三个现有 Prompt 都可选择对应人工标准；跨口径比较必须显式标识，不能只根据分数范围判断兼容。
- 内容准确性可导入留档，但继续排除评分、分位值和排名统计；可显示人工标注覆盖信息。

### 首版不扩展的功能

不建设多人在线标注/仲裁系统，不引入完整数据集管理平台，不改裁判 Prompt 或输出 Schema，不自动优化 Prompt。模型结果直接读取平台已有任务；外部模型结果 Excel 的独立导入适配可后续增加。

## 2. 已核对的代码基础与设计约束

| 现有能力 | 代码位置 | 对本功能的影响 |
| --- | --- | --- |
| 历史数据复用 | `web/server.py` 的 `/api/datasets`、`/api/datasets/{task_id}` | 数据来自历史任务快照，当前没有独立 dataset 数据库；首版基准自行保存案例目录即可 |
| 任务及逐题结果 | `web/tasks.py` 的 `Task`、`latest_results_by_index()` | 可提取最新逐题结果，但结果按 index 原位覆盖，不是完整不可变事件历史 |
| 补跑与更新批 | `web/runner.py`、`tasks.upsert_result_by_index()`、`merge_items_by_id()` | 同一 task_id 的结果或回答可能变化，报告不能只保存 task_id |
| 快照与导出 | `web/history.py` 的 `task_to_snapshot()`、`export_rows()` | 可复用快照读取；`updated_at` 每次抓取会变化，不能直接当结果版本 |
| 模型评分有效性 | `web/compare_statistics.py` 的 `score_state()` | 复用各协议的 Gate、适用性、核验和分数范围规则，不重新解释一套模型有效分规则 |
| 统计表结构/样式 | `StatisticsTable`、`web/compare_statistics_xlsx.py` | 复用表格结构和样式；人机样本集合单独计算 |
| 后台导出 | `web/exports.py` 的 `XlsxExports` | 其导出文件有 TTL，且工作开始时才抓取任务；不能直接当作长期保存的对比报告 |
| 前端 | `web/static/app.js`、`index.html`、`style.css` | 在结果区域增加按钮和独立面板，复用已有历史选择、分页和证据按需加载方式 |

还有三个不能误用的字段：

1. 导出为无题号旧记录补出的 `q{index}` 只是行位标识，不能自动用来跨文件匹配人工题号。
2. `options.product_names` 只是按产品位置排列的展示名称，不是稳定产品 ID。
3. `input_manifest_sha256` 包含协议、证据预处理和产品顺序，不能当作跨 Prompt 或产品换位时的回答身份指纹。

## 3. 页面流程

### 3.1 一个入口，面板内完成

结果页按钮：**与人工评分对比**。用户从历史记录加载任务后，也使用这个入口。无须先新增三个顶层菜单。

面板按以下顺序展开：

1. **选择人工基准**：已保存基准列表，或上传新 Excel；支持下载当前任务的空白人工标注模板。
2. **解析与映射**：自动建议工作表、表头、题号、产品身份、维度及 review 列；结构明确时展示摘要，未知结构才展开映射编辑。
3. **匹配预览**：显示题数、产品对应、回答核验情况、可评分标签数、未匹配和冲突清单。
4. **生成对比报告**：后台统计完成后显示概览、逐维度指标、产品差距和分歧明细。

“比较其他任务”是面板内的可选项，用于加入同批数据的其他 Prompt/模型任务，不增加新的启动评测流程。

### 3.2 需要用户明确的信息

- 人工基准名称、人工使用的标准；原 Excel 的“标准版本”若来自旧模型，只能作为推荐值。
- Excel 产品列与实际产品身份的映射；任务中的 answer1/2/3 与同一产品身份的映射。
- 历史数据缺少原始回答身份时，确认是否来自同一批原始回答；明确冲突不提供一键忽略。
- 裸 `N/A` 若要转换成“不适用”，需确认其标注意义；默认保留为“NA 原因未说明”。

这些选择属于数据定义，保存后可复用，不要求用户每次重复配置。

### 3.3 结果展示

| 区块 | 主要内容 |
| --- | --- |
| 概览 | 本次范围、匹配/核验情况、人工有效标签数、模型可比分数覆盖、完全一致率、MAE、平均偏差 |
| 维度分析 | 按产品和维度展开的一致率、误差、分档分布、混淆矩阵；均展示有效数与分母 |
| 产品差距 | 人工/模型均分、双向分位值、GSB、胜平负一致率和反转率 |
| 分歧明细 | 题号、产品、维度、人工分与来源、模型分与理由、分差、缺分/不适用状态、匹配强度 |

筛选项：产品、维度、场景、文字/VQA、录屏/长截图、模型偏高/偏低、分差、状态不一致。图表只使用当前表格的统计结果，不在前端另算分母。

证据按需打开。对比面板绑定明确 task_id/report_id；切换历史任务时取消旧请求或忽略旧响应，避免把上一任务报告显示在新任务下。

## 4. 人工 Excel 导入协议

### 4.1 当前文件的确定映射

原文件：`人工标注合并结果_20260904_2041.xlsx`。

- 工作表：`合并标注结果-review后`；152 条数据，152 个唯一 `query_id`。
- 忽略隐藏的 WPS 图片管理工作表。
- A：`query_id`；B：`题目`；C/D：产品录屏 URL；E/G：旧导出背景；F/H：旧导出回答文本。
- 产品1：小艺；产品2：豆包。只作为该导入适配器的建议映射，不写成所有数据集的固定产品名单。

| 维度 | 产品1人工最终分 | 产品2人工最终分 | review 优先列 |
| --- | --- | --- | --- |
| 理解需求 | AW | AX | 无 |
| 内容准确性 | BJ | BK | 无，留档不计主统计 |
| 服务闭环 | BU | BV | 无 |
| 场景化满足 | CF | CG | 无 |
| 直观高效 | CU | CV | CZ / DA |
| 有理有据 | DK | DM | DR / DS |
| 引导推荐 | ED | EE | 无 |

直观高效每个产品有 17 个非空 review；有理有据每个产品有 28 个非空 review，其中各包含 1 个 `N/A`。解析优先级必须按单元格是否真正为空判断。

原表含重复“胜负结果”表头，因此列映射内部使用工作表、表头行和物理列号，不用仅以表头文字为 key 的字典覆盖。上述列地址用于核对当前文件；实际适配还需核验对应表头，防止以后插列造成错位。

原表模型评分、模型 Gate、模型适用性、历史一致率列均不导入为人工标签。原始文件保留归档，但归档内容不会送入裁判。

旧导出中的“回答/背景”仅凭表头不能证明来自原始输入。记录 `answer_text_origin/context_origin`；默认 unknown，只作辅助核对。确认可追溯到源输入后才能参与回答指纹或硬冲突判断；若来自裁判转写，应明确标记且不用于硬判断。

### 4.2 平台提供的简洁宽表

一行一个 Case，包含：

- `case_id`、`query`，以及任务模板带出的产品、回答身份信息。
- `人工分_产品N_维度`；可选 `人工复核分_产品N_维度`、`人工批注_产品N_维度`。
- 可选 `人工是否适用_维度`、`人工响应Gate_产品N`、`人工安全Gate_产品N`。
- 可选 `人工评分状态_产品N_维度`，明确区分不适用、无法核验、Gate 阻断。

标准、分值范围、产品身份及模板版本放入“填写说明”工作表，导入时预填到确认界面。2/3 产品列动态生成，模板默认只含纳入统计的六个维度。模板中的人工分留空，不把模型分预填成人工答案。

保存映射时记录 `mapping_profile_id`、表头签名和列地址；再次上传表头不一致时重新预览，不能盲用旧列号。首版只支持宽表导入，内部统一转换成长表。

### 4.3 单元格解析规则

| 输入情况 | 规则 |
| --- | --- |
| review 非空 | 使用 review；即使值为 0 或 N/A，也覆盖基础人工分 |
| review 空白 | 回退基础人工分；基础也空白则未标注 |
| 数值 4、文本 `4`、`4.0` | 解析为整数 4，并按人工标准校验范围 |
| 0 | V0.3 合法；V0.2 两版越界；不能被当作空值 |
| `N/A`、`NA` | 默认 `na_unspecified`；仅经显式状态列/导入规则确认后转为具体空分原因 |
| 空单元格、全空白字符串 | `unlabeled`，不等于 N/A，不做向下填充 |
| 布尔值、非整数、`4分（有问题）`等混写 | 标记解析问题，不能截取第一个数字 |
| 公式 | 只读公式缓存且记录来源；无有效缓存提示另存计算结果，后台不执行公式或外链 |
| 重复题号、重复标签 | 列出冲突，不按最后一行覆盖，不取平均 |

题号按字符串处理，保留前导零，不进行数值化、大小写合并或模糊纠错。Excel 已经以数值存储而丢失前导零时，展示原值并要求修正/显式映射，不能猜测补零。

解析预览显示：总行数、有效 Case 数、有效标签数、空白数、NA 数、越界/格式问题和重复键。默认有冲突的版本不能发布；用户也可明确选择“仅保存有效记录”，但必须保存被排除清单和数量。

最终值选择后必须做跨字段校验：review 数字与显式“不适用”状态冲突、共享适用性=false却存在数字分、或人工 Gate 按对应人工标准已阻断但仍给数字分，都进入 `pending_conflict`。不得静默丢弃分数或覆盖状态。review=N/A 仅在显式状态或已确认转换规则无冲突时确定原因；否则仍为 `na_unspecified`。review为空白也不表示自动撤销基础标签；要撤销应修改基础标签或明确状态并通过校验。

## 5. 数据模型与存储

### 5.1 首版沿用本地 JSON 持久化

不要求现有任务新增人工评分字段。新增独立目录，全部放在已忽略的 `RUNS_DIR` 下：

| 路径 | 内容 |
| --- | --- |
| `human_imports/{import_id}/` | 上传原文件、解析预览、映射草稿；短期临时数据 |
| `human_baselines/{baseline_id}/v{version}/` | `manifest.json`、`cases.json`、`labels.json`、`states.json`、原始 Excel |
| `human_mappings/{mapping_profile_id}.json` | 已保存的列映射与表头签名 |
| `human_previews/{preview_id}/` | 本次匹配用的冻结任务结果与预览；短期临时数据 |
| `human_reports/{report_id}/` | `manifest.json`、冻结模型结果、匹配明细、指标及导出文件 |

基准发布后不可变，重新导入修改稿创建同一 baseline_id 的新版本；报告绑定明确版本。文件写入采用临时文件加原子替换，版本号更新使用进程内锁并核对预期版本，适配当前单服务进程架构。

正式基准和报告不沿用 XLSX 临时下载的 TTL。删除原评估任务不级联删除人工基准或已生成报告。首版不提供基准永久删除入口；可升级版本并选择其他基准。

### 5.2 HumanBaseline：基准元信息

```json
{
  "schema_version": "human-baseline-1.0",
  "baseline_id": "hb_example",
  "version": 1,
  "name": "问答评测人工参考",
  "human_standard_id": "qa_competitor_compare",
  "human_standard_version": "0.2-simplified",
  "human_policy_note": "按已确认的专家评分口径",
  "score_range": [1, 5],
  "dataset_name": "测评集名称",
  "case_catalog_sha256": "...",
  "source_file_sha256": "...",
  "sheet_name": "合并标注结果-review后",
  "mapping_profile_id": "map_example",
  "products": [
    {"product_id": "p_xiaoyi", "display_name": "小艺"},
    {"product_id": "p_doubao", "display_name": "豆包"}
  ]
}
```

产品 ID 首版在基准内稳定即可。一个品牌的基线版、实验版可以是两个不同 product_id，不能因为名称相同就自动合并。

基准案例目录存 `case_key`、外部 `case_id`、原问题/背景、题图引用和原图摘要、场景标签、每产品回答及身份信息。`case_key` 由基准案例目录命名空间和题号确定，不能把题号当成全平台全局唯一键。首版不强制给历史任务补 dataset_id。

### 5.3 HumanScoreLabel：人工标签长表

```json
{
  "case_key": "catalog_example:case_001",
  "product_id": "p_xiaoyi",
  "response_id": "response_example",
  "dimension_id": "intuitive_efficiency",
  "score_status": "scored",
  "score": 4,
  "annotation_stage": "review",
  "resolution": "accepted",
  "reason": "人工批注",
  "source": {
    "sheet": "合并标注结果-review后",
    "row": 2,
    "base_cell": "CU2",
    "review_cell": "CZ2",
    "selected_cell": "CZ2",
    "base_raw": "3",
    "review_raw": "4"
  }
}
```

上述数值仅为数据结构示意，不对应原表该单元格的实际标注。

唯一键：`baseline_id + version + case_key + product_id + response_id + dimension_id`。

`score_status`：`scored / not_applicable / unverifiable / gate_blocked / unlabeled / na_unspecified`。只有 `scored` 才允许数值分，其余必须为 null；`scored` 必须有范围内整数。导入错误存入校验明细，不伪装成正常 NA 标签。

`annotation_stage` 区分基础最终分与 review；`resolution` 区分 accepted 与 pending_conflict。只统计已接受的标签。不要求所有基础最终分都经过 review 才可使用。

### 5.4 人工状态标签单独存

- 适用性：`case_key + dimension_id → true / false / unknown`，对所有产品共享。
- Gate：`case_key + product_id + response_id + gate_id → pass / fail / unclear / unknown`。
- 保留 `source` 与是否由人工确认的转换规则派生。

不从模型状态填充人工状态，不因数字评分存在就假造人工 Gate 通过。不同产品的人工“不适用”标签与数值分冲突时进入待复核；未经确认不生成正式共享适用性标签。

首版不将旧表里自由填写的“胜负结果”混入评分推导结果。人机胜平负统一从各自有效分推导；若以后接入独立人工偏好标签，应另设指标并注明来源。

### 5.5 ComparisonReport：不可变报告

至少保存以下字段：

- `report_id`、`schema_version`、`metric_version`、创建时间与报告状态。
- `baseline_id/version`、人工标准及标签快照摘要。
- 每个模型任务的 task_id、协议 ID、bundle_revision、Prompt 哈希、裁判配置、结果快照摘要。
- 任务产品槽位映射、题号映射字段、案例范围、维度范围、身份确认记录。
- 每条匹配记录、有效/排除原因、逐题分差；各指标实际样本集合或可重建的匹配记录 ID。
- `compatibility_mode`：同标准 / 参考基准回归 / 不兼容。

报告保存计算所需的输入、人工标签与模型结果副本，不能仅保存到“最新版本”的引用。默认不复制原始大视频/图片，保存原始证据引用和已有摘要；媒体失效不影响已冻结指标读取，界面明确显示证据不可用。

### 5.6 MatchRow 与身份确认

每条对齐记录至少包含：`match_id`、`baseline_case_key/response_id`、`task_id`、`task_snapshot_sha256`、`task_item_index`、`source_case_id`、`task_product_slot`、`product_id`、`match_status`、`result_input_binding`、核验依据及排除原因。

身份确认另存 `match_ids`、`confirm_reason`、`confirmed_at`、`confirmation_scope_hash`。范围摘要覆盖基准版本、冻结任务输入/结果、产品映射及具体行集合；确认只对该范围生效。重新预览不得仅凭 task_id 继承旧确认；可复用产品列映射，但回答变更后的身份确认必须重新判断。报告恢复直接读取冻结的匹配/确认记录，不根据当前任务重新推定。

## 6. 题目、产品、回答的匹配算法

函数契约建议：

`align_baseline_to_run(baseline, run_snapshot, identity_mapping) -> MatchResult`

匹配函数不读网络、不调用模型；证据摘要准备与最终匹配分开。

### 6.1 对齐顺序

1. **确定本次范围**：默认以入口任务的全部 Case 为锚点；加入其他任务时仍沿用该范围，可显式选子集。人工文件额外题目列为范围外，不悄悄加入分母。
2. **提取真实题号**：明确选择 `item.id` 或 `item.source_data.query_id` 等真实源字段。不同候选 ID 相互冲突时要求选择，不依靠导出自动补号。
3. **建立一对一 Case 映射**：题号精确匹配；无 ID 时只给出候选，需用户提供明确映射，不用行号或相似 Query 自动绑定。人工表和任务都没有可恢复的真实题号时，先修正身份信息，不直接按显示顺序批量确认。
4. **映射产品身份**：每任务保存 `answer1 → p_xiaoyi` 等映射；产品换位后重新映射，统计输出按稳定产品身份排列。
5. **校验结果绑定**：确认该模型结果确实属于冻结的任务输入，而非更新批中断后留下的旧结果；具体规则见 §7.2。
6. **校验提问与回答**：核验问题、上下文、提问原图、原始回答或采集身份；裁判生成的转写不作为源回答变更的硬判断。
7. **生成匹配状态**：全部记录保留，统计只选择符合本次纳入策略的匹配项。

### 6.2 身份分层

| 情况 | 匹配结果 | 处理 |
| --- | --- | --- |
| 明确采集 ID 或原始内容摘要一致，问题/上下文无冲突 | `verified` | 自动纳入 |
| 题号一致、可见源文本一致，但旧视频 URL 与本地路径无法核验 | `identity_unverified` | 显示未核验数；确认“同一批原始回答”后记为 `confirmed` |
| 明确 Query、题图、源回答、背景或采集身份冲突 | `content_mismatch` | 排除，不能用批量确认覆盖 |
| 无对应题号/产品 | `unmatched` | 保留缺失明细，不给出分差 |
| 重复题号或映射到多个回答 | `ambiguous` | 排除并要求修正 |

`confirmed` 与 `verified` 的数量分别展示。确认只用于缺少历史信息，不把明确不同的回答视作同一个对象。

同一采集回答重新抽帧/切片：保留 response_id，记录证据视图版本不同；产品重新生成了回答：新 response_id，旧人工标签不自动继承。录屏换成长截图，只有能证明或确认它们展示同一次回答时才复用人工基准。

### 6.3 指纹定义

- `case_fingerprint`：原问题、公共上下文、明确多轮关系、提问原图摘要；不含 Prompt、模型或产品顺序。
- `response_fingerprint`：稳定产品 ID、源回答文本、产品背景、原始采集 ID/内容摘要；不含该产品所在槽位。
- `evidence_view_fingerprint`：实际采样帧或切片的摘要及预处理版本，独立于原回答身份。

没有足够信息时不生成“已验证”的结论。路径只作来源引用，路径相同不证明内容相同；不能用 basename 当身份。文本仅做版本化的轻量规范化（如 CRLF/LF），不删除标点、数字或大段空白后强行判等。

已有原图摘要可直接复用；本功能不为评分匹配自动下载 Excel 中的 URL。若需读取本地媒体计算摘要，沿用现有授权目录和后台文件读取规则，不占用模型请求额度。

现在读取媒体计算出的摘要只能证明当前文件内容，不能证明历史评测当时看到的内容。只有评测时已记录的摘要、采集 ID 或可信来源记录才能用于历史输入绑定证明；否则保留未核验状态。

## 7. 快照冻结、补跑与报告生命周期

### 7.1 冻结时机

匹配预览时冻结，生成报告时使用同一份预览快照。

1. `await peek_task_async(task_id)` 获取任务。当前异步函数仅接收 task_id，不传同步版本的 touch 参数。
2. 检查主任务处于终态、`active_runs == 0`、`repair_status` 不为 queued/running。仅看 `status == done` 不够，因为更新批期间主任务状态仍可能为 done。
3. 在事件循环内无 await 地完成状态检查和 `deepcopy(task_to_snapshot(task))`；随后才放入后台解析/匹配。
4. 对统计相关的规范化输入、逐题最新结果及协议做摘要；排除动态读取时间、页面展开状态、进度耗时等不影响评分的字段。
5. 保存 preview_id、snapshot_sha256、基准版本、映射和预览有效期。

预览期间若原任务又启动补跑，已经冻结的预览仍可生成报告；页面显示“基于预览时结果”。用户要分析新结果时重新预览并创建新报告。避免生成按钮点击后偷偷切换到最新结果。

### 7.2 最新结果的选择

- 复用 `latest_results_by_index()` 的既有“每个 Case 当前最新结果”语义，不挑选历史中分数最接近人工的一次。
- 取出结果后另做 `result_input_binding` 校验。现有文字任务更新 item 时可能保留旧结果，终态和 active_runs=0 不能保证结果来源一致。优先核对结果中原样保存的 query/context/answerN/contextN、评测时的证据摘要及可用调用记录；不是比较模型生成的转写。
- 在同一任务结果与输入之间，可以核对已记录的 `input_manifest_sha256`；它仍不能用作跨 Prompt 或产品换位的回答身份。明确绑定冲突记为 `stale_result`，排除并提示重新评测对应条目。
- 旧结果缺少绑定信息时记为 `binding_unverified`，与“人工基准—回答身份未核验”分开计数；仅凭基准与当前 item 相同不能标记 verified。用户明确确认旧结果所对应的回答来源后可作为 confirmed 样本纳入，报告保留确认依据。后续若需完整自动证明，可另行在 runner 内部增加输入来源摘要，不改变 Prompt。
- 成功补跑覆盖后的新结果在下一份报告中生效，不修改旧报告。
- 当前系统不保证保留每一次已被覆盖的结果，因此旧报告生成前已丢失的历史尝试不承诺恢复。
- 失败补跑不是独立重复实验；重复稳定性分析需要用户独立发起多个任务。

### 7.3 后台计算

报告状态：`queued → generating → ready / error`。使用独立后台任务与有限并发，文件解析和统计移到线程，不进入 EvalScheduler、不占百炼请求配额。

服务重启后：基准与 ready 报告仍可读取；未完成的报告标记中断，可从已冻结输入重新生成。报告计算具有固定输入与统计版本，可以安全重算，不能重新抓取活任务替代原输入。

## 8. 统计口径

默认排除内容准确性。所有指标保存数值、有效数、分母及排除原因；零分母输出 null，页面显示“—”，不输出 0% 或 NaN。

### 8.1 单产品维度评分

对产品 p、维度 d，在选定范围 T 内定义：

- `H(p,d)`：人工具有 accepted 且合法数字评分的 Case 集。
- `C(r,p,d)`：H 中与任务 r 身份已核验/已确认，且模型也具有有效数字分数的 Case 集。
- `N_H`、`N_C` 分别表示 H、C 的样本数；公式中的 M、H 分别指对应模型分和人工分。
- 模型有效性由对应冻结协议的 `score_state()` 决定；人工有效性来自人工标签本身。人工 Gate 缺失不自动删除已经确认的人工数字分，也不补出“通过”。

| 指标 | 定义 |
| --- | --- |
| 数值可比覆盖率 | `N_C / N_H`；模型失败、缺分、未匹配都体现在覆盖损失中 |
| 完全一致率 | `count(M = H) / N_C` |
| 差不超过 1 分比例 | `count(abs(M-H) <= 1) / N_C`；只在同一分制内解释 |
| MAE | `mean(abs(M-H))` |
| 平均偏差 | `mean(M-H)`，负值表示模型偏低 |
| 模型偏高/偏低比例 | `count(M>H)/N_C`、`count(M<H)/N_C` |
| 严重分歧比例 | `count(abs(M-H)>=2)/N_C`，明确是本分制中的分差阈值 |
| 分差/评分分布 | 输出每个合法分差与分档的数量；评分混淆矩阵用相同 C 集合 |

题号匹配率按 Case 数统计，数值覆盖率按产品×维度标签统计，界面明确单位。默认概览选择一个维度或展示完整六维表；如增加六维微平均，需明确按可比标签数加权，不能解释为产品综合质量总分。

### 8.2 NA 与状态

- 双方均 NA 不进入数字评分一致率。
- 分别统计：人机都有数字、人工数字/模型无数字、人工无数字/模型数字、双方无数字。
- 人工空白是未标注；裸 N/A 是原因未知；不能与明确“不适用”或模型技术失败合并。
- 适用性一致率使用双方都有明确适用性判断的 Case×维度；人工 unknown 不进入分母。
- Gate 一致率使用双方具有可比 Gate 判断的产品回答；人工/模型缺失和输入失败强制的 unclear 单独报告，不冒充有效 Gate 裁决。
- 原始 152 条人工文件没有独立人工 Gate/适用性列，相应正式指标显示“缺少人工标签”。经确认的 NA 映射可作为另行注明的派生口径。
- 最新“最终回复内部过程信息泄露”规则可能使原人工已评分的回答在模型侧被响应 Gate 阻断。这类记录计入覆盖损失及 Gate 阻断分布，不补0计算分差，不归为技术失败或人工不适用；没有独立人工 Gate 时仍不计算正式 Gate 一致率。

### 8.3 产品分位值与 GSB

对产品 A/B、维度 d、任务 r，定义 `P(r,A,B,d)`：人工 A/B 两分和模型 A/B 两分都有效、身份匹配通过的 Case 集。

在同一个 P 集上计算：

- `R_H = mean(H_A) / mean(H_B)`。
- `R_M = mean(M_A) / mean(M_B)`。
- 分位值偏差 = `(R_M - R_H) * 100` 个百分点。
- 人工/模型的平均分差、G/S/B 数量及比例、净胜率 `(G-B)/N`。
- 胜平负一致率 = 两侧 `sign(A分-B分)` 相同的题数 / N。
- 胜负反转率 = 一侧 A 胜、另一侧 B 胜的题数 / N；胜转平、平转胜在 3×3 混淆矩阵中另列。

分位值沿用平台现有“均分之比”，不是 P50/P90，也不是逐题分数比的平均；分母均分为零时不可计算。比例作为现有业务描述口径使用，不把 120% 解读成能力高 20%。

2 产品输出两个方向；3 产品输出三个产品对、六个方向。各产品对有自己的 P 集，不能因为产品 C 失败而删除有效 A/B 对。三产品整体排名一致率使用人机六个分数全部有效的集合，并以带并列关系的排名组比较，不强拆平局。该排名仅指单维度排名。

### 8.4 多 Prompt/多模型任务比较

同一人工基准可选择多个任务，报告同时保留两种口径：

1. **各任务覆盖及各自有效样本**：描述任务实际产出，展示 C/P 的覆盖情况。
2. **所有选定任务的共同有效样本**：对每个产品维度或产品对取各任务 C/P 的交集，重新计算指标并报告相对基线任务的变化。

不能直接把各任务不同样本上的一致率差称为 Prompt 提升。共同样本也要显示覆盖损失；没有共同样本时不排名，不输出虚构增益。

### 8.5 标准兼容规则

| 人工标准与模型标准 | 首版行为 |
| --- | --- |
| 相同标准及确认的评分口径 | 正常生成同标准对比 |
| 旧 V0.2 与评分校准版 | 允许显式选择“相对既有人工基准的回归比较”；分别标注人工口径、模型协议、实现版本 |
| V0.2 的 1—5 分人工标签与 V0.3 的 0—3 分 | 阻止数字评分/分位值一致性报告，提示选择对应人工基准；不做线性换分 |
| 未记录人工标准 | 要求导入时选择并记录依据，不能默认等于当前模型任务标准 |
| 未识别的模型标准或冻结修订号 | 可显示匹配情况，暂停正式分数统计并列出原因 |

同分制不是同标准的充分条件。已有样本参与过 Prompt 优化时，基准用途标为 development/regression；holdout 用途需来自未参与调参的新样本。平台不能仅凭一个用途标签证明不存在数据污染。

当前代码基线的 `6c05c20` 修改了 Prompt 与共享内部过程规则，但未改变注册表中的 bundle_revision。因此，已有协议 ID 加 bundle_revision 不能单独证明使用了完全相同的 Prompt。报告必须按 task_id 和结果快照分别保存运行，并保留每条结果实际记录的 prompt_sha256、可用的裁判调用记录及已知源代码提交。历史缺少这些信息时注明“实际 Prompt 信息不全”，不能用当前源码补写历史事实。

现有 prompt_sha256 是渲染后的 system/user 内容摘要，包含题目输入；它用于追溯逐题调用，不作为跨题目的模板版本分组键。多任务报告先按各任务分别统计、再使用共同有效样本比较，不因协议版本号相同就合并为同一种 Prompt。该设计不改变既有补跑的协议恢复行为，也不承诺仅凭旧版号重建当时的模板。

加权 Kappa、按会话/重复 Query 分组的置信区间可作为下一阶段扩展，首版优先确保覆盖、分母、MAE、偏差及产品差距口径正确。

## 9. 后端接口设计

新增接口与现有 `/api/parse`、`/api/eval` 分开。以下路径为设计建议，实施时统一沿用项目现有错误响应形式。

| 接口 | 输入/输出与作用 |
| --- | --- |
| `GET /api/eval/{task_id}/human-template` | 返回当前任务的空白人工宽表模板；声明人工标准；不预填模型分 |
| `POST /api/human-baselines/imports` | multipart 上传 xlsx；返回 import_id、可见工作表、列索引、少量样例、建议映射 |
| `POST /api/human-baselines/imports/{import_id}/preview` | 工作表、表头行、人工标准、产品与列映射；返回解析摘要、错误及少量规范化标签 |
| `POST /api/human-baselines` | 按 import_id 和预览摘要发布基准；可带既有 baseline_id、expected_version 创建新版本 |
| `GET /api/human-baselines` | 分页/搜索基准列表，返回版本、标准、产品、Case 数和标注维度 |
| `GET /api/human-baselines/{id}/versions/{version}` | 返回版本元信息与分页标签预览 |
| `POST /api/human-comparisons/preview` | 入口 task_id、其他 task_ids、baseline_id/version、产品/题号映射、比较范围；冻结并返回匹配预览 |
| `POST /api/human-comparisons` | preview_id、预览配置摘要、明确的身份确认项及兼容模式；返回 report_id/status=queued |
| `GET /api/human-comparisons?task_id=...` | 列出该任务已有报告，支持重新打开 |
| `GET /api/human-comparisons/{report_id}` | 返回任务状态、固定报告元信息和聚合指标 |
| `GET /api/human-comparisons/{report_id}/rows` | 按维度/产品/分差等过滤的分页匹配与分歧明细 |
| `GET /api/human-comparisons/{report_id}/download` | 下载由同一冻结报告生成的 Excel |

映射模板随基准发布可选保存，初期可通过基准列表选用既有 mapping，无须增加单独映射管理页面。

首版上传检查、解析预览和匹配预览均通过 `await asyncio.to_thread(...)` 完成后返回 HTTP 200；设置上传大小及行数上限，不设计未配套的预览轮询接口。只有报告生成返回 HTTP 202，随后通过报告 GET 接口轮询状态；约 1 秒起步，完成或关闭面板即停止，不增加 SSE 事件类型。

业务错误示例：400 文件结构错误；404 任务/基准不存在；409 任务仍活跃、预览过期或版本冲突；422 产品映射、标准、标签校验失败。错误响应包含可定位的工作表/行/列及问题类型。

`POST /human-comparisons` 只允许在冻结预览上补充“身份信息不足”的确认。修改产品映射、题号映射、标准或过滤条件必须重新预览。重复点击同一预览和相同配置返回同一 report_id，避免重复计算。

### 复用的函数边界

- 复用 `peek_task_async()`、`task_to_snapshot()`、`latest_results_by_index()` 抓取当前任务。
- 模型侧适配到 `Case` 后调用 `compare_statistics.score_state()`，并使用 `DIMENSION_NAMES`、`SCORE_DIMENSIONS`。
- 新的人机统计独立计算集合；不能把人工标签伪装成另一份模型任务直接调用 `build_compare_statistics()`，否则 Gate/缺分分母会错。
- `compare_protocols.py` 只读取协议元信息，本功能不修改现有三个 Prompt。
- 不把人工表写入 `Task.items`、`source_data`、`reference` 或裁判调用参数，防止标签混入被评输入。
- 原评估 Excel 导出保持独立；对比面板导出专门的人机报告，避免同一任务绑定不同人工基准后，普通导出含义变化。

openpyxl 用于应用内的确定性读表，建议 `read_only=True` 读取评分区域，并保留公式/缓存标识。模板与人机报告沿用现有 OOXML 表格和统计样式，由新增导出模块组装；不重写原完整评测 XLSX 导出器。

## 11. Excel 报告结构

文件名建议：`数据集名_人工基准vN_人机对比_报告ID.xlsx`。

| Sheet | 内容 |
| --- | --- |
| 对比概览 | 人工/模型版本、本次范围、覆盖指标、核验强度、排除原因、用途与统计口径 |
| 人机评分统计 | 产品×维度的人工/模型均分、完全一致率、差≤1分、MAE、平均偏差、高低分偏差 |
| 产品差距对比 | 两产品双方向/三产品六方向的人工与模型分位值、均分差、GSB及结论一致性 |
| 分歧明细 | 一行一个匹配标签，人工来源、模型结果、分差、状态及证据引用；可筛选 |
| 匹配与排除 | 全部 Case/产品匹配结果、身份核验/确认依据、未匹配与冲突，避免只有成功记录 |
| 统计口径 | 公式、分母、兼容模式、共同样本定义、基准/任务/指标版本与快照摘要 |

多任务时在表中增加任务/Prompt 和“各自样本/共同样本”列，不为每个任务无限复制整套 Sheet。评分混淆矩阵和分差分布放在评分统计表的独立区块。

数值列写为 Excel 数值类型，比例使用百分比格式；页面与 Excel 消费同一个 report 数据，不分别实现统计公式。首版报告不嵌入全部原视频/长图，提供来源与按需查看入口。

## 13. 实施顺序与交付门槛

1. **基准导入与保存**：数据模型、两类模板、列映射、review/NA解析和版本保存。用当前152题文件核对解析结果。
2. **单任务对齐与统计**：任务快照、产品映射、身份核验、完全一致率/MAE/偏差/分位值/GSB，先通过手算测试。
3. **页面与报告导出**：接一个结果页入口，完整走通上传或复用→预览→报告→Excel；已有历史任务可用。
4. **多任务共同样本与回归**：加入其他Prompt/模型任务，完成共同样本对比、版本隔离、补跑后快照不变和前端兼容验证。

上述四步共同构成首版完成条件。实现准备完成后再运行必要的聚焦测试与一次全量回归，并记录界面截图；本设计轮不执行代码修改或部署。
