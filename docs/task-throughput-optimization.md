# 单任务吞吐优化与耗时分解

> 本文的预算与性能数据属于历史版本。2026-09-17 的模型默认预算、并发调节和升级要求见[裁判模型与思考模式](judge-model-thinking.md#限流与部署范围)。

基线为 `feat/bailian-request-throughput` 的 `eab257e`。此次保留评测提示词、
评分协议、图片分辨率、帧选择和输出内容，优化本地准备、额度记账及观测。

## 改动与原因

- 文本按随包提供的 Qwen3.5 分词器计数，保留 10% 文本余量和消息开销；
  不再把 UTF-8 字节数直接当作 Token。分词完全离线，词表固定版本、校验
  SHA-256，并带原许可证。缺失依赖时使用原保守估算并记录警告。
- 图片保持原有保守的 32 像素网格估算，读取 Base64 头部即可获得尺寸，
  避免为了估算而反复解码整张图片。不会改变实际上传的图片。
- 收到成功 HTTP 响应头后，将输入预留转成独立的 60 秒账目；长时间生成
  的输出继续预留。原实现把整份输入与输出一直保留到请求结束，会将
  “每分钟预算”变成更低的“所有未完成请求总量”上限。
- 返回 usage 后替换估算，不重复记账。无 usage、取消、断流仍保守保留
  完整估算，避免失败重试绕过额度。输出预留在有 3 个样本后使用最近
  20 次最大输出的 1.25 倍，最低 1024；大输出会立即提高估算。
- 等待期间重新读取最新估算，让已完成请求带来的校准及时作用于排队项。
- 媒体准备复用已获得的视频时长，以及单次抽帧中的解码/布局特征；每次
  抽帧的缓存上限 8 MiB，处理结束释放，不跨任务保存视频内容。测试和
  基准验证选中帧与元数据一致，生产运行无需重复执行旧版。

默认仍为连续 1 秒最多 9 次 HTTP 尝试、480 RPM、80 万估算 TPM；重试和
JSON 修复也经过限制。媒体并发默认为 4，可由管理员设置
`AUTO_EVAL_MEDIA_CONCURRENCY=1..16`，页面显示实际配置。提高媒体并发只在
媒体处理是瓶颈且服务器资源足够时有益。

输入、输出分开记账与官方“输入事前预扣、输出事后结算”的思路一致；这里
额外保留输出预留，输入窗口从收到响应头才开始计时，偏向保守。
[阿里云限流应对最佳实践](https://help.aliyun.com/zh/model-studio/rate-limiting-best-practices)。

## 152 条固定负载对照

使用真实旧、新生产控制器和相同提示词。模型响应由虚拟时钟模拟，不发送
真实请求；图片为 1280×720 合成图，usage 假设由本地分词及固定图像网格
计算，响应头在 5 秒返回。媒体准备不计入此表，避免把两个实验的收益相乘。

| 每题图数 / 输出 Token / 响应总时长 | 基线总时间 | 优化后总时间 | 吞吐提升 |
| --- | ---: | ---: | ---: |
| 12 图 / 3,000 / 90 秒 | 895.38 秒 | 611.34 秒 | 1.46 倍 |
| 40 图 / 6,000 / 120 秒 | 2,055.75 秒 | 1,209.10 秒 | 1.70 倍 |
| 12 图 / 12,000 / 150 秒 | 1,818.84 秒 | 1,049.42 秒 | 1.73 倍 |

三组均完成 152 条，发送次数符合连续一秒限制。12 图样例的首次输入估算
由 84,832 降至 31,586；40 图由 117,762 降至 64,516。下降来自计数校正，
实际发给模型的提示词和图片没有缩减。模型本身的固定响应时间未变化，
因此首条结果仍分别是 90、120、150 秒。

这些数字是可复现的**离线调度对照**，不是服务器真实模型实测。实际收益
受图片数量、模型速度、usage、网络及其他共享账号调用影响。多图请求可能
先达到 Token 限额，不能把“8 次/秒目标”理解成每种请求都能达到。

复现（使用项目环境）：

```powershell
$env:PYTHONPATH = 'C:\workspace\auto_eval_vqa\src'
& C:\workspace\venv\Scripts\python.exe scripts/benchmark_task_throughput.py --baseline-ref eab257e --output docs/task-throughput-benchmark.json
```

## 媒体阶段对照

60 秒、720×1280 合成录屏，3 轮中位数：7.35 秒 → 4.76 秒（1.55 倍，
耗时降低 35.3%）。选中帧 SHA-256 和完整抽帧元数据逐项一致。实验期间
有其他测试负载，绝对耗时会波动；此数字仅代表该媒体阶段。

回归结束后另用仓库复现脚本做了一轮执行检查：4.28 秒 → 3.76 秒，耗时
降低 12.2%，帧与元数据仍一致。不同系统负载下收益有波动，35.3% 不应视为
固定保证。

`scripts/benchmark_media_preparation.py` 提供可移植复现：自动生成合成录屏，
交替执行当前代码与指定基线，并强制检查帧和元数据一致。

## 验证

- 完整非集成回归：437 项通过，包含限速、取消、重试、媒体及评分流程。
- 7 组前端脚本检查通过；真实 Vue 页面验证展开/折叠及结果耗时展示。
- Wheel 构建通过，并检查分词器、许可证均包含在安装包中，词表哈希一致。
- 152 条虚拟时钟基准三组通过；媒体基准校验选中帧 SHA-256 和抽帧元数据。

这些验证未调用真实模型，未消耗百炼额度；尚未验证服务器部署后的实际耗时。

## 更新与边界

拉取代码后必须使用服务环境安装依赖（`pip install -e ".[web]"`），以安装
新增的 `tokenizers`。词表已随包提供，运行时不会从 Hugging Face 下载。
更新依赖并重启服务后，新任务才使用此次优化；重启会中断正在运行的任务。

仍限定同一进程/事件循环共享预算。图片估算、服务端模板和未知长输出会有
误差，无法承诺消除所有 Token 429；当前保留 usage 校准、错误退避与冷却。
