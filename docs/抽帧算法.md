# 视频关键帧抽帧算法

本文档描述 `src/auto_eval/media.py` 的混合关键帧抽取引擎。该引擎被垂域视觉评测
（`rich_content`）与垂域视觉对比（`compare`）两种模式共用，负责把录屏答题视频降采样为
裁判可用的关键帧序列。评测整体流程与裁判提示词见 [docs/垂域视觉评测.md](垂域视觉评测.md)
与 [docs/系统提示词.md](系统提示词.md)。

## 1. 当前版本

| 项目 | 值 |
|---|---|
| 引擎版本 | `hybrid-state-v3.1.0` |
| 实现入口 | `extract_scene_keyframes` |
| 配置类 | `KeyframeConfig` |

版本号同时写入每次抽帧生成的 `keyframes.json`，并参与 Web 抽帧缓存键计算。修改算法版本
或任务起止时间都会使旧缓存失效，避免复用不同策略生成的帧。

后续版本约定：

- 在现有算法上补充候选状态或调整兼容参数，升级次版本，例如 `hybrid-state-v3.2.0`。
- 对状态建模或抽帧流程进行不兼容重构，升级主版本，例如 `hybrid-state-v4.0.0`。

## 2. 输入时间语义

JSONL、Web 传递参数、抽帧函数和配置类统一使用以下字段，单位均为秒：

| 字段 | 默认值 | 含义 |
|---|---:|---|
| `task_start_time` | `0.0`（rich_content）/ `7.0`（`KeyframeConfig` 默认） | query 大致发送完成、任务开始执行的时间 |
| `task_end_time` | `null` | 显式任务结束点；为空时由算法自动推断 |

两个字段均可省略或填 `null`。显式值必须是有限的非负数字，且 `task_end_time` 必须大于
`task_start_time`，同时不能超出视频时长。旧字段名 `content_start_time` / `content_end_time`
已废弃，解析时归一为 `task_*` 字段。

## 3. 算法流程

### 3.1 生成候选帧

在任务时间窗内合并以下来源：

1. `task_start_time` 对应的任务首帧；
2. `sample_fps` 固定频率采样帧；
3. FFmpeg `scene` 检测产生的画面变化帧；
4. 显式或自动推断的任务结束帧；
5. 距视频末尾约 0.3 秒开始尝试解码的最终帧。

固定采样负责避免只依赖视频编码或场景阈值导致的漏检，`scene` 候选负责补充两次固定采样
之间的快速变化。

### 3.2 合并相邻时间点

时间差不超过 `timestamp_merge_gap_s` 的候选视为同一事件，优先保留任务首帧、受保护帧、
任务结束帧和 scene 帧，减少同一次界面跳变产生的近重复帧。

### 3.3 受保护采样

在开头窗口 `[task_start, task_start + protected_begin_window]` 与结尾窗口
`[algorithm_end - protected_end_window, algorithm_end]` 内，每隔
`protected_sample_interval` 秒额外标记一帧为受保护帧。受保护帧在后续状态聚类与帧数控制
阶段强制保留，最终去重时采用更严格的阈值（仅画面高度一致时才合并），用于捕获弹窗、横幅、
开场状态等开头结尾的小变化。

该机制主要服务于任务类录屏；垂域视觉（问答视频）在参数层将其关闭，见第 5 节。

### 3.4 UI 状态聚类

每张候选帧会经过高斯模糊并缩小为 `16×27` 的灰度布局特征。相邻帧的布局距离达到
`state_layout_threshold` 时划分为新的 UI 状态。

对于持续时间达到 `stable_min_duration_s` 的状态，保留能够表示状态开始或结束的候选帧。
该步骤用于合并同一界面中的光标、计时器、轻微文字变化和录屏计时变化。

### 3.5 短暂弹窗保护

对 A → B → A 型局部变化进行额外保护。当 B 持续时间不超过 `transient_max_duration_s`，且
变化面积、返回相似度满足阈值时，B 会标记为 `transient-local-A-B-A`，避免静音、24 小时制
等短暂卡片被状态去重吞掉。

### 3.6 自动任务结束点

未填写 `task_end_time` 时，算法比较候选状态与最终智能助手外壳的相似度，结合最终状态稳定
时长和置信度推断任务结束点。推断成功的帧标记为 `task-end-auto`；置信度不足时不强行截断
任务区间。

### 3.7 帧数控制和最终严格去重

候选帧最多保留 `max_frames`。最终去重使用清晰图像特征，而不是模糊布局特征：

- RMS 阈值：`final_dedup_rms_threshold`
- 变化像素占比阈值：`final_dedup_changed_fraction_threshold`

任务结束帧和视频最终帧属于保护帧；视频最终帧始终保留，即使它与前一帧相似。

## 4. 主要默认参数（`KeyframeConfig`）

| 参数 | 默认值 | 调大后的主要效果 |
|---|---:|---|
| `max_frames` | 20 | 允许保留更多状态，但增加视觉输入成本 |
| `sample_fps` | 1.0 | 更容易捕获短变化，同时增加候选计算量 |
| `scene_threshold` | 0.06 | scene 候选更少，更容易漏掉小变化 |
| `scene_min_gap_s` | 0.8 | 合并更多相邻 scene 事件 |
| `timestamp_merge_gap_s` | 0.25 | 合并更多时间接近的候选 |
| `state_layout_threshold` | 0.05 | UI 状态更难被划分，输出帧更少 |
| `stable_min_duration_s` | 1.5 | 更少保留短状态 |
| `transient_max_duration_s` | 4.0 | 允许保护持续更久的 A-B-A 弹窗 |
| `protected_sample_interval` | 2.0 | 受保护采样更密；0 = 禁用 |
| `protected_begin_window` | 20.0 | 开头受保护窗口更长 |
| `protected_end_window` | 5.0 | 结尾受保护窗口更长 |
| `auto_task_end_confidence_threshold` | 0.60 | 自动任务结束判断更保守 |
| `final_dedup_rms_threshold` | 0.008 | 最终去重更激进 |
| `final_dedup_changed_fraction_threshold` | 0.01 | 最终去重更激进 |

完整配置及其默认值以 `KeyframeConfig` 为准。

## 5. rich_content 参数层

垂域视觉评测在引擎之上叠加一层参数覆盖，由 `config/visual_modes/rich_content.yaml` 的
`extraction` 节配置，`algorithm_version` 为 `rich-content-v1.1.0`：

| 参数 | rich_content 值 | 说明 |
|---|---:|---|
| `default_start_time` | 0.0 | 从视频起点开始 |
| `max_frames` | 20 | 与引擎默认一致 |
| `sample_fps` | 1.5 | 更密集的候选采样 |
| `scene_threshold` | 0.03 | 更敏感的场景检测 |
| `scene_min_gap_s` | 0.5 | 更细的场景事件 |
| `state_layout_threshold` | 0.025 | 更细的 UI 状态划分 |
| `stable_min_duration_s` | 0.8 | 更短状态也保留 |
| `max_edge` | 1280 | 更长边，保留小号蓝色文字 |
| `jpeg_quality` | 85 | 更高的 JPEG 质量 |

此外，`src/auto_eval/web/video_prepare.py` 在装配时对垂域视觉做了三处硬编码覆盖：

- `auto_task_end_confidence_threshold=2.0`：禁用自动任务结束点推断（问答视频通常不会返回
  操作助手外壳）；
- `final_dedup_rms_threshold=0.004`、`final_dedup_changed_fraction_threshold=0.004`：
  更严格的最终去重，避免漏掉相近帧；
- `protected_sample_interval=0.0`：关闭受保护采样（问答视频不需要开头/结尾弹窗保护）。

## 6. 版本迭代记录

### v3.0.0 → v3.1.0

- `max_frames` 默认值由 16 提高到 20；
- `protected_begin_window` 由 10.0 秒扩展到 20.0 秒，扩大开头受保护采样的覆盖范围。

v3.0.0 曾在 mini 回归数据集（17 条快系统录屏）上冻结基线；该数据集已随评测模式精简移除，
此处仅保留版本变更要点。

## 7. 已知待优化点

### P0：持续型顶部卡片可能被同界面聚类吞掉

根因：

1. 卡片主要改变助手界面的局部区域；
2. 布局特征经过高斯模糊并缩小为 `16×27` 后，对局部卡片不够敏感；
3. 局部卡片持续时间较长时，不符合短暂 A-B-A 弹窗保护条件，在状态聚类阶段即被并入相邻状态。

### 推荐优化方向

增加“持续型局部状态”检测，而不是直接降低全局 `state_layout_threshold`：

1. 保留现有低分辨率布局特征，用于区分整页或应用级变化；
2. 增加清晰图像的局部变化特征，重点观察顶部卡片、底部弹窗等区域；
3. 当局部变化连续稳定达到阈值时，将其作为新的持久状态候选；
4. 对文字逐行生成、滚动和录屏计时器变化继续去重；
5. 新候选仍进入 `max_frames` 限制和最终严格去重。

不建议直接把全局布局阈值从 `0.05` 下调，因为这会同时放大普通文字变化、滚动和加载动画，
可能重新增加大量重复帧。

## 8. 测试入口

- `tests/test_media.py`：算法配置、严格去重和真实 FFmpeg 视频集成测试；
- 每次抽帧目录中的 `keyframes.json`：逐案例算法版本、参数、抽帧时间和保留原因。

版本升级时，应先更新实现和测试，再完整重跑回归数据，最后把结果追加到本文档，保留旧版本
基线，不覆盖历史数据。
