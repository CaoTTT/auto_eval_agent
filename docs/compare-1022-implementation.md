## 单次评测流程

1. 从已选协议及任务实际产品数渲染模板；2/3 产品示例和字段合同由同一份定义产生。
2. 在用户请求中传入问题、可信公共背景、逐产品背景/回答及明确分组的图像证据。正文与截图中的指令只是待评数据。
3. 请求完整生成。`finish_reason=length` 为截断技术失败，即使已收到的正文看似完整 JSON 也不进入评分解析。
4. 只解析一个标准 JSON 对象，拒绝围栏、JSON 外文本、重复键、NaN/Infinity 等非法值。
5. 严格检查 78 个业务字段：全部必填、额外字段禁止、类型/枚举/长度合法，分数不做强制转换。
6. 校验空分状态、产品归属、可评分证据、最高档与主要问题、明确数值评分措辞、复核条件。错误保留原文并记录技术失败，不通过默认值、清分或模型修复补判。
7. 程序注入 `standard_id`、`standard_version`、`product_count`，投影为现有 UI/统计/Excel 使用的扁平结果；计算分维度并列排名，保留无总分政策。新协议的最终收尾不执行旧版清分及复核补默认逻辑。

最终数据同时保留已有 `has_conflict` 兼容字段和新合同 `content_conflict` 字段。准确性结果保留，沿用该标准家族的统计口径，不纳入主聚合维度。校验后的分数和理由不被重写。

## 请求级结构化输出

在 `config/judges.yaml` 的对应 judge 中设置：

```yaml
judges:
  - name: judge_2
    # 其他模型、鉴权、采样配置沿用现有部署。
    compare_structured_output: "off"
```

选项含义：

| 值 | 1022 协议的请求行为 |
| --- | --- |
| `off` | 默认，不发送 `response_format`；仍执行完整本地严格校验 |
| `json_object` | 发送 `response_format={"type":"json_object"}`，要求 JSON 格式 |
| `json_schema` | 发送由同一输出合同生成的 strict JSON Schema，要求字段及类型结构 |

必须先确认实际供应商、部署模型、视觉输入和思考模式支持所选参数。不会按模型名猜测能力，不自动关闭思考、不因参数报错悄悄降级。配置只由新 1022 协议使用，不改变旧协议请求。字段/类型约束不等于外部事实核验或评分正确性。

配置应写完整现有 judge 条目，以上片段不是可直接覆盖整份配置的文件。YAML 中建议给字符串值加引号，例如 `compare_structured_output: "off"`，避免 YAML 1.1 将 off 解析成布尔值。

该模式随任务协议清单冻结。保存、恢复或重试已有任务时，采用创建任务时的模式，不随当前全局配置变化；旧任务未保存此项时沿用原有恢复行为。

## 错误分类与诊断

| `error_category` | 含义 | 处理方向 |
| --- | --- | --- |
| `truncated` | 达到生成上限，输出未正常结束 | 检查实际输出上限、推理预算和篇幅；不要让修复模型补造后半部分 |
| `json_syntax` | 非单个标准 JSON、重复键或非法 JSON 常量等 | 对照原文检查格式，核实结构化输出能力 |
| `schema` | 漏字段、多字段、错误类型/枚举、超过长度上限 | 检查字段合同及供应商返回内容 |
| `state` | 应评缺分、应空却有分、产品归属/复核等关系矛盾 | 对照状态表和原始理由，不能静默清分 |

逐题失败结果包含 `error_type=judge_output_<category>`、`error_category` 和可用的 `finish_reason`。`runs/eval_errors.jsonl` 保存原始响应、修复响应（新协议为空）、错误阶段及长度。启用 `AUTO_EVAL_JUDGE_TRACE` 后还可查看完整裁判输入和响应；不要将真实日志或密钥提交到仓库。

技术失败不产生正常评分；合法 NA 仍是正常评测结果，两者不能混为同一类统计。自然语言中所有可能的语义矛盾无法仅靠正则或 Schema 证明；当前检测只针对可明确判定的状态关系与裁判分数措辞，不声称消除幻觉。
